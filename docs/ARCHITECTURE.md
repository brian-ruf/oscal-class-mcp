# OSCAL MCP — Architecture

## Principle

The server is a thin, well-typed MCP facade over the `oscal` library. It holds **no**
OSCAL parsing or mutation logic of its own; it translates MCP tool calls into library
calls and shapes the results into JSON-safe responses.

## Layers

```
server.py            FastMCP app assembly + transport (stdio default)
  state.py           support-DB configuration (once, before any OSCAL use) +
                     DocumentStore (handle <-> OSCAL cache over oscal.Workspace)
  serialize.py       OSCAL object -> JSON-safe summary / validation report
  tools/             content, validation, conversion, query, imports, support
  resources/         about, api_reference (+ search_library_api), concepts,
                     knowledge_search (search_knowledge), metaschema, recipes, standard
  recipes/*.md       curated library-usage patterns
  knowledge/         bundled offline docs + version-parity helpers
    oscal_lib/       oscal library operating-concept guides (synced from a release)
    oscal_std/       curated NIST OSCAL-standard snapshot (synced) +
                     additional_notes.md (authored expert notes) + NIST-ATTRIBUTION.md
scripts/
  sync_knowledge.py  dev/release-time bundler for oscal_lib + oscal_std (not runtime)
```

- **Authored vs synced.** Everything under `knowledge/` is sync-generated **except**
  `oscal_std/additional_notes.md` (expert commentary) and `oscal_std/NIST-ATTRIBUTION.md`,
  which are hand-authored and preserved across syncs. Changing the notes is a versioned
  release event — see `docs/MAINTAINING_KNOWLEDGE.md`.

- **Version parity.** `knowledge/__init__.py` exposes the installed `oscal` version and
  the source release each bundled doc collection was synced from. `oscal-lib://about`
  reports both; `build_app` logs a warning when they drift. Bundled docs keep the server
  working **offline** while a manifest ties them to a specific `oscal-class` release.

- **Stateful cache.** `DocumentStore` wraps `oscal.Workspace`, the library's own
  document registry. Handles (`doc-1`, …) are stable per underlying object; re-opening a
  source returns its existing handle. MVP eviction triggers: explicit `close_document`
  and process exit. (Richer TTL/content-change invalidation remains a future
  negotiation item.)
- **Support database.** Configured exactly once at startup via
  `state.configure_support_db`, before any OSCAL object is created, so the library never
  falls back to a CWD-relative path. `db_init_mode="auto"` auto-extracts the bundled DB.
- **Library-only guarantee.** Only `serialize.py` reads fields off OSCAL objects, and
  only via public methods/properties (notably `json_query_one` for live metadata, which
  is authoritative where the cached `.title`/`.version` attributes can lag).

## Forward compatibility

The `oscal` library is under active development and will gain getters/setters per model.
The API reference and `search_library_api` are generated by runtime introspection
(`oscal.gendocs.collect_api`) of the installed package, so new symbols surface
automatically. Phase-2 model-specific authoring tools will plug into the same
`register(mcp, store)` pattern.

## Missing-capability hand-off

If an OSCAL operation an agent needs is not yet in the `oscal` library, do not work
around it in this server. Add a `docs/handoff-<topic>.md` describing the requirement,
the expected API shape, and the required return contract, for the library maintainer.

## Coexistence

Tool names are unprefixed and plain; resources use the dedicated `oscal-lib://` scheme.
This avoids collisions with other OSCAL MCP servers (`awslabs/mcp-server-for-oscal`, the
`metaschema-framework/claude-plugins`) and shares no state or database with them.
