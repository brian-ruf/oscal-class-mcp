# Maintaining the bundled knowledge

The server ships three bodies of offline documentation under
`src/oscal_mcp/knowledge/`, surfaced as `oscal-lib://` and `oscal-std://` resources. This
doc explains how each is refreshed and versioned.

## 1. Library API reference — automatic

`oscal-lib://api` / `search_library_api` are generated by **runtime introspection** of the
installed `oscal` package. Nothing to maintain; they always reflect the installed version.

## 2. Library operating-concept guides — synced from a release

`oscal-lib://concepts` is a snapshot of `oscal-class/docs/*.md`, kept in parity with the
`oscal` library release the server wraps.

```bash
# from a local checkout (stamp the matching release):
python scripts/sync_knowledge.py oscal-lib --from-local /path/to/oscal-class --release vX.Y.Z
# or straight from a GitHub tag:
python scripts/sync_knowledge.py oscal-lib --from-release vX.Y.Z
```

Refresh this whenever the `oscal` dependency pin moves. `oscal-lib://about` reports
`parity.status` (`ok` / `mismatch` / `not-bundled`) comparing the installed library to the
bundled docs' `source_release`.

## 3. NIST OSCAL standard snapshot — curated, from OSCAL-Pages

`oscal-std://concepts` is a curated snapshot of the NIST "Learn" pages
(`usnistgov/OSCAL-Pages`), public domain / CC0. Hugo front-matter and shortcodes are
stripped; see `knowledge/oscal_std/NIST-ATTRIBUTION.md`.

```bash
python scripts/sync_knowledge.py oscal-std --check         # is newer NIST content available?
python scripts/sync_knowledge.py oscal-std                 # incorporate latest, pin the SHA
python scripts/sync_knowledge.py oscal-std --from-release <sha-or-tag>   # pin a specific ref
```

**Detection & memory.** The manifest (`knowledge/oscal_std/_manifest.json`, committed to
the repo) remembers the exact `source_ref` (commit SHA), `source_branch`, and
`source_commit_date` that were bundled. `--check` compares that against the newest upstream
commit touching the content path and **writes nothing**; its exit code is a build gate:
`0` up-to-date, `1` update available, `2` check failed. A plain `sync oscal-std` resolves
the tracked branch's latest commit and pins it, so **new builds pick up the latest NIST
content by default** while staying reproducible. Run `--check` (or a plain sync) when cutting
a release; see Phase 4's `publish.yml`.

The curated page allow-list lives in `OSCAL_STD["pages"]` in `scripts/sync_knowledge.py`.
Add/remove pages there, then re-run.

## 4. Expert notes (`additional_notes.md`) — authored, versioned, release-gated

`knowledge/oscal_std/additional_notes.md` holds **authored expert commentary** (draft-status
caveats, known gaps NIST does not state explicitly). It is hand-maintained and is **never**
overwritten by the sync script.

**Every substantive change to the notes is a release event.** When you add or revise a note:

1. Edit `additional_notes.md`; follow the per-note template at the bottom of that file
   (assign the next `N-###` id).
2. Bump `notes-version` (semver) in **both** the top `<!-- notes-version: … -->` comment
   and the visible heading, and add a **changelog** row.
3. **Bump the `oscal-mcp` version** in `pyproject.toml` (a notes addition ⇒ at least a
   patch/minor release) and record the shipping version in the notes changelog.
4. Re-run `python scripts/sync_knowledge.py oscal-std` so the manifest re-records the
   `notes_version` (it is surfaced by `oscal-lib://about`).

This keeps the authored guidance traceable: each notes version maps to an `oscal-mcp`
release, and consumers can see the notes version via `about`.
